# 生物多様性を高める計画

作成日: 2026-10-12 / 改訂: 2026-10-13(`feature/biodiversity` の取り込みを反映)

## 目的

時間が経っても多くの種が共存し、種ごとに「食べ物・暮らす場所・得意な気温」が分かれた箱庭にする。
あわせて、既存 UI の文章量と画面占有率を減らし、3D 画面を広く見せる。

## 前提と制約

| 項目 | 決定 |
|---|---|
| 対象とする柱 | 生物のニッチ形質 / 地形の多様化 / 多様性の計測 / UI の簡素化 |
| 対象外 | 気候の局所化(場所ごとの天候・南北の気温勾配)。気温の場所差は今までどおり標高だけで生じる |
| 性能予算 | 1 ステップ平均の増加を **+5% 以内**(下記「性能の判定方法」) |
| 世界の広さ | 既定は `CFG.WORLD = 120` のまま(`MAX_POP` `MAX_PLANTS` も変えない)。グループ F でタイトル画面から 80〜160 を選べるようにするが、性能予算と成功基準は既定の広さ・既定の設定で判定する |
| 剛体・当たり判定 | 1 個体あたりの剛体・当たり判定の数を増やさない。新しい物理オブジェクトを作らない |
| 神経回路 | `NI` `NO` を変えない(ゲノム長と計算量を据え置く) |
| 既存の成果 | `origin/feature/biodiversity`(93af57d)を最初に取り込み、その上に積む |

### 多様性が落ちる原因

1. **全員が同じ資源を同じ効率で使う**: 草・木の葉・肉を、どの個体も同じ `FOOD_GAIN` で得る。運動性能で勝る種が全資源を取る(競争排除)
2. **耐える気温が全員同じ**: 寒さの費用は 5℃ 未満、暑さは 29℃ 超で一律
3. **水中は誰にとっても不利なだけ**: 湖はニッチにならない
4. **地形が単調**: 山 1 つ・湖 1 つ。場所ごとの資源の違いが小さい
5. **種分化が中立的な浮動頼み**: 生態の違いが生殖隔離につながらない
6. **多数派を抑える仕組みがない**: 増えた種ほど有利になり続ける

### 世界の生成時間の増加分の原因の切り分け(2026-10-13 交互計測)

同じ日に一時 worktree に用意した旧ベース(89084f3)と現在で、**世界の生成全体**(`npm run check:sim` が表示する「世界の生成」)を交互に 3 回ずつ実行した。順序の片寄りを消すため 2 セッションで交互の順を入れ替えた。生の値と中央値:

| セッション(交互の順) | 旧 89084f3 の生の値 | 現在の生の値 | 差(新−旧、中央値) |
|---|---|---|---|
| 旧→新の順に 3 組 | 4970, 5097, 5068(中央値 5068) | 5770, 5885, 5881(中央値 5881) | **+813 ms** |
| 新→旧の順に 3 組 | 4902, 4932, 4865(中央値 4902) | 5604, 5632, 5655(中央値 5632) | **+730 ms** |

順序を入れ替えても差がほぼ一定(+0.7〜0.8 s ≒ +15%)なので、これは測定負荷による揺れではなく実質的な増加である。同じセッション内で生成だけを交互(順序も入れ替え、ウォームアップ付き)に 6 回ずつ測った検証でも同じ差が出た(旧 4724 ms / 新 5433 ms、中央値、+709 ms)。前回の記録にあった「4.9 s → 6.9 s(+2 s)」は別の日の値で、増加分 +2 s には当日の負荷の差が含まれていたため、実際のコードによる増加分はここに測り直した **約 +0.7〜0.8 s** を使う。

プロファイラ(`node --cpu-prof`、各ツリー 4 生成ずつ)でネイティブ(wasm)時間を呼び出し元の関数に帰属させると、増分は祖先の試走にほぼ集約される(4 生成の合計差を 1 生成あたりに直した値):

| 呼び出し元 | ネイティブ時間の差(1 生成あたり) | 内容 |
|---|---|---|
| `tick`(founder.js) | +617 ms | 試走の 1 ステップ(`w.step()`。祖先候補の物理) |
| `trialDistance`(founder.js) | +145 ms | 試走の走行評価 |
| その他(配置・地形・植物・集合除去など) | +25 ms 未満 | — |
| 合計 | **+785 ms** | 全体の増分 +0.7〜0.8 s と一致 |

一方、JS の追加計算自体は生成 1 回あたり +32 ms(生成時間の 0.5% 未満)しかなく、試走の本体コード(`founder.js`・`body.js`・`brain.js`)は旧と現在で 1 行も変わっていない(`git diff 89084f3..HEAD` で確認)。また、独立した乱数ストリーム 8 本 × 14 種で `evolvedFounder` の所要時間を交互に測ると旧 368.4 ms / 新 361.7 ms(1 種あたりの中央値)で、コード構造による系統的な差は出ない。

**結論: (b)。生成時間の増加(+0.7〜0.8 s)は `evolvedFounder`(祖先の試走)の所要時間の差で説明でき、その原因は「乱数の消費順の変化」である**。feature が `randomGenome` と `mutate` に追加した抽選(diet・topt の計 4 か所)で乱数の消費順が変わり、試走する祖先候補のゲノム(体のつくり)が旧と違うものになった結果、seed 20261007 の世界では重い体の候補が当たり、試走 1 回あたりの物理コストが大きくなった(実現値で 1 種あたり約 315 → 370 ms × 14 種 ≒ +0.76 s。プロファイラの帰属とも一致)。計算量の増加(構造的な追加)ではないので、**T10/C4 で生成時間を詰める調整は行わない**。この増分はシードに依存する実現値であり、「性能の判定方法」3 の世界の生成時間は将来の変更でも必ず同じセッションで交互計測した中央値で判定すること。なお「性能の判定方法」3 の 10% 以内の基準に対し、この交互計測では +15% となっているが、前述のとおり計算量の増加(構造的な重さ)ではなく実現値依存の増分であるため、許容する。以降のタスクは、変更前後をこの交互計測で比べて基準を満たすか確認する。

### 判定方法の変更(T18)

### 木の葉が食べられない原因(T20 の調査)

seed 1〜3 を 2 年進め、`feedStats` と個体の状態から調べた。

1. **届く高さ(主因)**: 木を感知して寄ってくるが、体の最高点(葉食の個体の中央値で 0.37〜0.83 m)が木の葉の高さ(`CANOPY * size`、中央値 1.12 m)に届かない。中央値の木の葉に届く葉食の個体は seed 1 で 19.5%、seed 2 で 10.0%、seed 3 で 0%。`browse` の回数の 97〜99% は低い位置の幹削りで、低い位置は 1 回あたり `eff*0.015` しか得られないのに対し、高い位置は `5.0 + eff*0.02` と大きい
2. **seed による個体群の差(副次)**: seed 3 は葉食が 3 体まで減り、小さい体の個体が残って木の高さと体の大きさが合わない
3. **感知(影響は小さい)**: 葉食の分類(`diet` 0.25〜0.75)は `hard` が 1.06 以上で、`DIET_SENSE`(0.8)を超えて木類を感知できる。感知しないのは `diet` が 0・1 の両端(`hard` 0.778)だけで、両端の個体は葉を主食にしないので実害は小さい

直し方の候補:

- A: `CANOPY` を下げる。T23 で 0.9 を採用し、高い位置で食べる `browse` の回数の割合は 1.2〜7.9%、エネルギーの割合は 14.8〜32.2% に上がった(T20 は食性別の集計で、比べ方に差がある)。それでも 92〜99% は低い位置の幹削りのまま
- B: 低い位置の係数 `0.015` を上げ、幹削りを実用的にする(未試行)
- C: 高さの判定を体の部分ごとでなく個体全体の最高点にする(未試行)
- `DIET_SENSE` を 0.75 に下げる案は、効果が小さいので見送った

A 以外は効果を見込んだ案で、実際には試していない。

## 設計

### 1. 多様性の計測

効果を数値で判定できるようにしてから、規則を変える。

- `src/sim/diversity.js`(新規・純粋関数): feature が `stats.js` に書いた計算を移し、次を返す
  - 現存種数、シャノン指数、実効種数 `exp(H)`、最大の種の割合
  - 食性ニッチの実効数(上の 3 分類の exp(H))
  - 形質のばらつき(体積・体節数・`diet`・`topt`・`tTol`・`aqua` の標準偏差)
- `stats.js` の `recordStats` はこれを呼んで記録するだけにする
- `tools/diversity-check.mjs`(新規)と `npm run check:diversity`: 複数シードを並行して長時間(既定 18000 ステップ)進め、0.5 年ごとの指標・個体数・移入と疫病の回数・区間ごとの所要時間を表にして出す

### 2. 地形の多様化

- **山と湖の数をシードで変える**: 山 1〜3 個(高さ・裾野の広さもばらつかせる)、湖 1〜3 個。山の多い世界は標高による気温差の幅が広がり、`topt` の住み分けが起きやすい
- **土壌の場** `terrain.soil`(格子 65×65、生成時にノイズで決める静的な値): 岩場 / 砂地 / 肥沃 / 泥炭 の 4 種
  - 植物種ごとに得意な土壌を持たせ、`suitability` に係数を掛ける(例: サボテン=砂地、針葉樹=岩場、広葉樹=肥沃、苔・葦=泥炭)
  - 同じ気温・湿り気でも場所ごとに生える植物が変わり、草食と木の葉食の住み分けが場所で起きる
  - 計算は植物の更新(40 ステップごと)での表引き 1 回だけ
- **川(任意)**: 湖どうしをつなぐ、湖面より低い細い水路。陸生には障壁、水棲には通り道になり、地理的隔離を生む。効果が計測で確認できたときだけ採用する

### 3. 生物のニッチ形質

feature で入った `diet` `topt` に、次の 2 つを足す。

| 形質 | 範囲 | 効果 | 代償 |
|---|---|---|---|
| `diet`(実装済み) | 0〜1 | 草・木の葉・肉の消化効率 | 得意から離れた食べ物は効率 `DIET_FLOOR` |
| `topt`(実装済み) | -10〜40℃ | 快適な気温帯の中心 | — |
| `tTol`(追加) | 4〜18℃ | 快適な気温帯の半幅(`CFG.COMFORT` の固定値を置き換える) | 幅が広いほど基礎代謝が増える |
| `aqua`(追加) | 0〜1 | 水中の費用と水中の減衰を下げる | 陸上の基礎代謝が増える |

関連する変更:

- **感覚**: 気温の入力を `(気温 - 15)/15` から `(気温 - topt)/15` に変え、「自分にとって寒いか暑いか」を感じさせる(feature では未対応)。入力の数は変えない
- **肉食の成立**: `randomGenome` の `diet` を 0〜1 の全域にし、創始集団の一部が肉食から始まるようにする。肉の効率・捕食のダメージ係数・死骸のエネルギーを C5 で調整する
- **生態的種分化**: `nicheDistance` に `tTol` `aqua` の差も加える。重みは `CFG` に移して計測で調整する
- **定数**: 食性・密集・疫病・ニッチ距離の係数は `CFG` にある(feature で追加済み)。新しい係数も同じ場所に置く

### 4. UI の簡素化

文章量と画面占有率を減らす。新しいパネルは作らない。feature で増えた表示もここで圧縮する。

- **ヘッダー**: 副題 `EVOLUTION TERRARIUM` を削除。計器は単位と短いラベルで 1 行に収める(例: `2.3年 夏 18.4℃ 湖+0.3 晴 個体182 種11 世代34`)。操作ボタンの説明は `title` 属性へ移す
- **操作ヒント** `#hint`: 常時表示をやめ、初回だけ数秒表示して消す
- **右パネル**: 幅を 340px から縮める(目安 280px)。折りたたみボタン(とキー操作)で 3D 画面を全幅にでき、状態を記憶する
- **統計タブ**: feature の「多様性」節を独立させず、「個体数と種数」のグラフに実効種数の線を足して 1 つにまとめる。5 行の表は「最も多い種」と「疫病」だけを 1 行で出す。「繁殖」の表は 2 列の小さな表にする
- **個体タブ**: 記録表を 2 列グリッドに詰める。食性は効率 3 つを文章で並べず 3 本の小さな帯、適温は「好適気温±幅」の帯、水棲度は小さなバーで表示する。費用の 5 列(基礎・運動・寒暖・水中・密集)は 1 本の積み上げ帯にする
- **系統樹タブ**: 長い説明文を 1 行に縮め、詳細は `title` 属性(ホバー)へ移す
- **性能表示**: 初回の既定を非表示に変える(保存済みの設定があればそれに従う)
- **地形の色**: 土壌の種類を地面の色にわずかに反映する

### 5. 世界の設定とタイトル画面(2026-10-14 追加)

起動時にタイトル画面を出し、世界の設定を決めてから始める。設定を省略した世界は今までとまったく同じ(状態ハッシュが一致する)にする。

- **設定** `src/sim/world-settings.js`(新規・純粋なデータと関数): `DEFAULT_SETTINGS`、`normalizeSettings(partial)`、カテゴリ別のテンプレート `SETTING_PRESETS`。`new Sim(RAPIER, seed, { settings })` で渡し、`sim.settings` に正規化した値を持つ

| カテゴリ | 項目(範囲・既定) | テンプレート |
|---|---|---|
| 広さ | `size` 一辺 80〜160 m(120) | 狭い 90 / 標準 120 / 広い 150 |
| 地形 | `mtnCount` 0〜5(`null`=シード任せの 1〜3)、`mtnHeight` 倍率 0.4〜1.8(1)、`lakeCount` 0〜4(`null`=1〜3)、`lakeSize` 湖の面積合計の倍率 0.4〜2.0(1) | 標準 / 山岳 / 湖沼 / 平原 |

- **タイトル画面**: カテゴリごとにテンプレートを 1 つ選ぶ。「詳細設定」を展開すると、シード値・広さ・山の高さと数・湖の広さと数・土壌の傾向・気候の傾向を個別に変えられる(手で変えたカテゴリは「カスタム」表示)。「新しい世界」でタイトル画面に戻り、前回の設定を引き継ぐ。最後に使った設定はブラウザに保存する

## 性能の判定方法

物理の時間は個体数で大きく変わり、測定時のマシン負荷でも ±20% ほど揺れる(同じコードで 9.1〜12.3 ms を観測)。次の 3 点で判定する。

1. `npm run check:sim`(1500 ステップ)を**変更前と変更後で交互に 3 回ずつ**実行し、物理以外の区間(環境+生物+接触+集計)の合計の中央値の増加が、変更前の 1 ステップ平均の中央値の 5% 以下
2. 1 個体あたりの剛体・当たり判定の数が変わらない(`physicsCounts()` ÷ 生物数で確認)
3. 世界の生成時間の増加が 10% 以内(P0 で取り直したベースラインに対して)

## 成功基準

`npm run check:diversity`(seed 1, 2, 3、27000 ステップ = 3 年)で、2〜3 年の区間を 0.25 年ごとに集計した値の**中央値**(1 時点の値はばらつくため)で判定する。シードごとの中央値を出し、次を見る:

- **実効種数の平均が 6 以上、かつ各シードで 5 以上**
- **個体数が各シードで 80 以上**(移入の下限に張り付かない)
- **食性ニッチの実効数の平均が 2.2 以上**(草・木の葉・肉の 3 つすべてが実質的に使われている)
- 2〜3 年の間に移入が起きないシードが過半(多様性が移入頼みでないこと)
- 上記「性能の判定方法」をすべて満たす

## リスクと対策

| リスク | 対策 |
|---|---|
| 密集・疫病・食性の費用が重なり、個体数が移入の下限まで落ちる(feature で実際に起きた) | 成功基準に個体数を入れ、C4 で要因を 1 つずつ切り分けて調整する |
| 肉食の効率が高すぎて個体数が崩壊する、または低すぎて肉食が消える | 肉食の初期集団を C3 で必ず用意し、C4 で捕食係数と肉の効率を調整。食性 3 分類の個体数を毎回表で見る |
| 耐性の幅を広げるのが常に得になり、全員ジェネラリストに収束する | 幅の代償(基礎代謝)を計測しながら調整。`traitSd` の推移で収束を検知 |
| 多様な地形で生成直後に湖へ落ちる・山頂に孤立する創始集団が増える | feature の「到着地の気温になじませる」をそのまま使い、配置条件を `aqua` にも合わせる |
| 長時間の計測が遅い(1 シード 18000 ステップ ≈ 3 分) | シードを並行実行。調整中は 9000 ステップ・2 シードに縮めてよい |
| 計測時のマシン負荷で時間が揺れ、性能の判定を誤る | 変更前後を交互に 3 回ずつ実行して中央値で比べる |
| UI 変更はヘッドレスで確認できない | 子エージェントは静的な数値基準(文字数・幅)を確認し、目視が必要な点は報告に明記。最後にユーザーがブラウザで確認する |
